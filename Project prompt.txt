I'm building a PROTOTYPE for a fleet management web app for a bank's internal Group Forensic Services (GFS) team, to demo to leadership before requesting cloud infrastructure. This tracks pool vehicle bookings, manager approval of requests, physical key handover, check-out/check-in with photo evidence, and service scheduling. It handles sensitive forensic-adjacent data, so audit trails and data integrity matter even at prototype stage, since the demo needs to show these controls working, not just the UI.

IMPORTANT: This must run entirely locally, no cloud dependencies, since I don't yet have Azure access. It should be structured so it can migrate to Azure SQL, Azure Blob Storage, and Azure Entra ID later with minimal rework.

WORKFLOW THIS APP SUPPORTS:
1. User logs in (mock login for now) with a role of either Employee or Manager
2. Landing page shows both vehicles and their current status (Available, Reserved, In Use, Under Maintenance), and if not Available, who currently has it or has requested it
3. An Employee requests a vehicle, either immediately or as an advance reservation, providing a Purpose/Reason for the trip and a Destination. This creates a Booking in "Pending Approval" status
4. A Manager sees pending requests (with reason and destination visible) and can Approve or Reject them
5. Once Approved, the Employee must collect the key in person from the Manager who approved it. The Manager confirms this in the app (KeyCollected = true, KeyCollectedTimestamp set) before the Employee can proceed to Check-Out. Check-Out must be blocked, both in the UI and at the API level, unless KeyCollected is true
6. Employee completes Check-Out: photo capture of vehicle condition via camera, odometer/mileage entry, current location
7. When the vehicle is returned, the Employee completes Check-In: photo capture, mileage, location, optional damage flag. If damage is flagged, an Incident record is automatically created for Manager review
8. The Manager then confirms the key has been physically returned (KeyReturned = true, KeyReturnedTimestamp set), which closes out the booking
9. All create/update actions are written to an AuditLog table (who did what, when, old value, new value)
